1. SYSTEM ARCHITECTURE & HIGH-LEVEL OVERVIEW
--------------------------------------------------------------------------------

The fraud monitoring system is designed as an asynchronous, near-real-time 
streaming pipeline that monitors 100% of switched transactions without 
interfering with or adding latency to core payment switching operations.

DATA FLOW DIAGRAM:
------------------
[ Payment Switch Core ]
       │ (Writes transaction logs: XML / JSON)
       ▼
[ Log Shipper Agent (Vector / Filebeat) ] 
       │ (Tails log file in real-time, <50ms latency)
       ▼
[ Message Queue: Apache Kafka ]
       │ Topic: "switching-raw-logs"
       ▼
[ Stream Parser Service (Python / Go) ]
       │ Normalizes ISO 20022 (pacs.008, pacs.002) and REST JSON
       ▼
[ Message Queue: Apache Kafka ]
       │ Topic: "switching-normalized-tx"
       ▼
┌────────────────────────────────────────────────────────┐
│ STREAMING FRAUD EVALUATION ENGINE                      │
│                                                        │
│  1. In-Memory State & Velocity Engine (Redis)          │
│     - Sliding window: 1 min, 5 min, 1 hour, 24 hours   │
│     - Tracks account frequency, sums, fail rates       │
│                                                        │
│  2. Deterministic Rule Engine                          │
│     - Blacklist / Watchlist checks                     │
│     - High-velocity spikes (e.g. >5 tx/min)            │
│     - Sudden large single-amount threshold             │
│                                                        │
│  3. AI / Machine Learning Engine (Scoring: 0-100)      │
│     - Phase 1: Isolation Forest (Anomaly Detection)    │
│     - Phase 2: LightGBM / XGBoost via ONNX Runtime     │
└──────────────────────────┬─────────────────────────────┘
                           │
       ┌───────────────────┴───────────────────┐
       │ (Score >= 80 or Rule Triggered)       │ (All Transactions)
       ▼                                       ▼
[ Instant Notification ]              [ High-Speed Analytics DB ]
  • Telegram Bot Alerts                 • ClickHouse Database
  • Bank Risk API Webhooks              • Audit trail & reporting
  • Email / SMS Alerts                         │
                                               ▼
                                      [ Real-time Dashboard ]
                                        • Grafana / Custom Web UI

2. HARDWARE & INFRASTRUCTURE REQUIREMENTS
--------------------------------------------------------------------------------

Because tabular fraud detection models (Isolation Forest, XGBoost, LightGBM) run 
efficiently on modern CPUs, NO EXPENSIVE GPU SERVERS ARE REQUIRED.

Recommended Server Sizing for 500 - 2,000 Transactions Per Second (TPS):

A. Development / PoC Environment (Single Machine / PC):
   • CPU      : 8 Cores (Intel Core i7/i9 or AMD Ryzen 7/9 / Xeon)
   • RAM      : 16 GB - 32 GB RAM
   • Disk     : 256 GB NVMe SSD
   • OS       : Windows 10/11 Pro (with WSL2 & Docker Desktop) or Linux (Ubuntu 22.04+)

B. Production Deployment (Distributed 3 Nodes / VMs):
   • Node 1 (Ingestion & State):
     - Role   : Apache Kafka + Redis Cluster
     - Specs  : 8 vCPUs, 32 GB RAM, 500 GB NVMe SSD
   • Node 2 (AI Processing & Parser):
     - Role   : Parser Worker + AI Scoring Engine (ONNX Runtime)
     - Specs  : 16 vCPUs, 32 GB RAM, 256 GB SSD
   • Node 3 (Analytics & Dashboard):
     - Role   : ClickHouse Database + Grafana + Web UI
     - Specs  : 16 vCPUs, 64 GB RAM, 2 TB NVMe SSD (RAID 10 recommended)

5. DATA SCHEMAS & MESSAGE SPECIFICATIONS
--------------------------------------------------------------------------------

A. Input Formats from Payment Switch:
   1. ISO 20022 XML:
      • pacs.008.001.xx (Financial Institutional Customer Credit Transfer)
      • pacs.002.001.xx (Payment Status Report - Success / Fail confirmation)
      • Key fields extracted:
        - GrpHdr/MsgId             -> Transaction Reference ID
        - IntrBkSttlmAmt           -> Amount & Currency
        - DbtrAgt/FinInstnId/BICFI -> Debtor (Sender) Bank Identifier
        - DbtrAcct/Id/Othr/Id      -> Debtor (Sender) Account / Wallet
        - CdtrAgt/FinInstnId/BICFI -> Creditor (Receiver) Bank Identifier
        - CdtrAcct/Id/Othr/Id      -> Creditor (Receiver) Account / Wallet
        - CreDtTm                  -> Transaction Timestamp

   2. REST API JSON (Mobile App / QR Payments):
      • Direct fields:
        {
          "txn_id": "TXN998234",
          "sender_inst": "BANK_A",
          "sender_acc": "0100928371",
          "receiver_inst": "WALLET_B",
          "receiver_acc": "2099384711",
          "amount": 5000000.0,
          "currency": "LAK",
          "timestamp": "2026-10-19T14:40:00Z",
          "status": "SUCCESS"
        }

B. Normalized Internal Data Model (Canonical Schema):
   Every incoming transaction will be converted into this standard JSON schema:
   {
     "tx_id": string,
     "timestamp": string (ISO 8601),
     "channel": string ("ISO20022" | "REST_API" | "QR"),
     "source_bank": string,
     "source_account": string,
     "dest_bank": string,
     "dest_account": string,
     "amount": float,
     "currency": string,
     "status": string ("SUCCESS" | "FAILED" | "PENDING"),
     "response_code": string,
     "risk_score": integer (0 - 100),
     "risk_reasons": list[string]
   }

6. STEP-BY-STEP IMPLEMENTATION ROADMAP
--------------------------------------------------------------------------------

PHASE 1: Infrastructure Deployment (Local Docker Setup)
-------------------------------------------------------
• Set up `docker-compose.yml` defining Kafka, Redis, ClickHouse, and Grafana.
• Initialize ClickHouse tables for transactions and fraud alerts.
• Verify local connectivity and ports.

PHASE 2: Real-time Ingestion & Normalizer (Parser)
--------------------------------------------------
• Configure Vector (or Filebeat) to monitor switch log directories.
• Develop `normalizer.py`:
  - Consumes from Kafka `switching-raw-logs`.
  - Determines if payload is XML (ISO 20022) or JSON (REST).
  - Normalizes fields and publishes to `switching-normalized-tx`.

PHASE 3: Redis Velocity Engine (Rule-based Detection)
-----------------------------------------------------
• Develop `velocity_engine.py`:
  - Sliding Window in Redis (Sorted Set `ZADD` with TTL).
  - Calculate 1-minute, 5-minute, 1-hour transaction counts per account.
  - Calculate 1-hour cumulative amount per account.
  - Check against Blacklist / Watchlist sets in Redis.
  - Trigger instant rules:
    * Rule 1: More than 5 transfers from 1 account in 60 seconds (Card/Account draining).
    * Rule 2: Single transfer exceeding configured high-risk threshold.
    * Rule 3: High failure velocity (>3 failed transfers followed by 1 large transfer).

PHASE 4: AI Anomaly Detection Engine
------------------------------------
• Develop `ai_engine.py`:
  - Extract feature vector per transaction:
    [amount, hour_of_day, velocity_1m, velocity_5m, amount_ratio_to_avg]
  - Run Isolation Forest (Unsupervised) for zero-day anomaly scoring.
  - Compute normalized Risk Score (0 - 100).
  - Append evaluation result to the transaction payload.

PHASE 5: Alerting & Storage Pipeline
------------------------------------
• Stream all evaluated transactions into ClickHouse for historical auditing.
• If `risk_score >= 80` or Rule Triggered:
  - Format instant alert payload.
  - Dispatch to Telegram Bot channel.
  - Send asynchronous Webhook to Bank/Fintech Risk API.

PHASE 6: Real-time Operational Dashboard
----------------------------------------
• Configure ClickHouse datasource in Grafana.
• Build monitoring panels:
  - Current System TPS (Transactions Per Second).
  - Real-time Fraud Alert Feed (Table with Red Highlights).
  - High-risk source accounts & destination accounts.
  - Anomaly distribution heatmap by institution.
